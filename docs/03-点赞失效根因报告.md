# QQ空间自动点赞「静默失效」根因报告

> 本文记录了一次完整的真机排查过程：**接口一直返回成功，日志一直打印「已点赞」，但空间里就是没有赞**。
> 结论是 **3 个独立缺陷叠加**造成的，其中 2 个会让功能「看起来正常、实际什么都没做」。
>
> 📌 **隐私说明**：为保护当事人隐私，文中的 QQ 号、好友昵称与动态 ID 均已替换为**等长占位符**
> （QQ 号 → `10000000xx`，动态 ID → `aaaa1111bbbb2222cccc000x`，昵称 → `好友A/B/C…`）。
> 除此之外的日志、响应体、参数与结论均为实测原文，未作改动。

---

## 一、现象

在某台服务器上部署 AstrBot 4.29.0 + 本插件（上游 v3.1.3），使用纯 Cookie 模式（`qzone_cookie`），配置为每 2 小时自动点赞一次好友动态。

**日志表现完全正常：**

```
[AutoLike] 本轮检查 5 条动态，新点赞 5 条，跳过已赞 0 条，去重库共 5 条
已点赞 → 好友A
已点赞 → 好友D
已点赞 → 好友C
已点赞 → 好友B
```

**但用户在 QQ空间里刷新后：被"点赞"过的动态，点赞列表里没有自己。**

这正是上游 README 长期挂着的那句话：

> `[x] 点赞说说（接口显示成功，但实测点赞无效）`

---

## 二、关键认知：日志和返回值都不能作为证据

排查中最重要的一个转折点：**必须找到一个"裁判"**。

- ❌ **不能信日志** —— 上游的 `like_posts()` 调完接口不检查返回值，直接打印「已点赞」。
- ❌ **不能信接口返回** —— 点赞接口对「首次点赞」「重复点赞」「参数被忽略」三种情况**返回完全一样**：

```json
{
    "code": 0,
    "subcode": 0,
    "message": "succ",
    "default": 0,
    "data": ""
}
```

- ❌ **详情接口没有点赞字段** —— `emotion_cgi_msgdetail_v6` 的响应里搜不到任何 `like` 相关字段，无法用来核对。

### ✅ 真正的裁判：好友动态流 HTML 里的点赞按钮

`feeds3_html_more` 接口返回的 HTML 中，每条动态的点赞按钮都带着**真实状态**：

```html
<a class="item qz_like_btn_v3 item-on"
   data-islike="1"          <!-- 1 = 我点过赞，0 = 没点过 -->
   data-likecnt="13"        <!-- 真实点赞总数 -->
   data-showcount="12"
   data-unikey="http://user.qzone.qq.com/1000000002/mood/aaaa1111bbbb2222cccc0002"
   data-curkey="http://user.qzone.qq.com/1000000002/mood/aaaa1111bbbb2222cccc0002">
```

于是可以**闭环自动验证**：点赞前记录 `data-islike` → 调点赞接口 → 重新拉动态流 → 看 `data-islike` 有没有从 `0` 变成 `1`。
（本仓库的 `tools/qzone_check.py` 就是这个思路的成品工具。）

用这套方法测出的结果：

| 动态 | 调用点赞接口前 | 调用后 | 判定 |
|---|---|---|---|
| `user.qzone.qq.com/1000000001/mood/9bbc00dc...` | `islike=0 likecnt=0` | `islike=0 likecnt=0` | ❌ **赞没点上** |
| `user.qzone.qq.com/1000000003/mood/0d78b599...` | `islike=0 likecnt=3` | `islike=0 likecnt=3` | ❌ **赞没点上** |

**结论：接口返回 `succ` 是假象。**

---

## 三、根因（3 个独立缺陷）

### 根因 1：`unikey` / `curkey` 必须用 `http://`，插件用了 `https://` ★ 核心

点赞接口 `internal_dolike_app` 的 `unikey`/`curkey` 参数，**决定了"给哪条动态点赞"**。

**浏览器实际发送的**（从动态流 HTML 的 `data-unikey` 属性直接读出来）：

```
http://user.qzone.qq.com/1000000001/mood/aaaa1111bbbb2222cccc0001
^^^^^^ http
```

**插件发送的**（`core/qzone/api.py` 的 `like()`）：

```python
"unikey": f"{self.BASE_URL}/{post.uin}/mood/{post.tid}",   # BASE_URL = "https://user.qzone.qq.com"
"curkey": f"{self.BASE_URL}/{post.uin}/mood/{post.tid}",
```

`BASE_URL` 是 `https://user.qzone.qq.com`，于是 `unikey` 变成了 `https://...`。

**服务端的行为**：既不报错也不点赞，直接返回 `{"code":0,"message":"succ"}` 把你糊弄过去。

**验证**：把同一段请求里的 `unikey`/`curkey` 换成 `http://` 前缀，其它参数一字不改，再调一次：

```
发送点赞（http:// unikey）: {"code":0,"subcode":0,"message":"succ","default":0,"data":""}

=== 点赞后状态 ===
   islike=1 likecnt=1    http://user.qzone.qq.com/1000000001/mood/aaaa1111bbbb2222cccc0001  <== 目标
```

`islike` 从 `0` 变成 `1`，`likecnt` 从 `0` 变成 `1` —— **成功**。

> ℹ️ 社区 PR [Zhalslar/astrbot_plugin_qzone#47](https://github.com/Zhalslar/astrbot_plugin_qzone/pull/47) 早已指出这一点，但被作者关闭，理由是「这个接口实际上是有效的，只是文档忘改了」。
> 实测证明：**PR 的判断是对的**，`https://` 版本确实点不上。本 Fork 采纳了该修复，并做成 `like_use_http_key` 开关（**默认开启**）。

---

### 根因 2：`data` 是字符串导致点赞流程崩溃

`core/qzone/client.py` 的 `request()` 里有这么一行（上游原样）：

```python
if (
    resp.status == HTTP_STATUS_UNAUTHORIZED
    or parsed.get("code") == QZONE_CODE_LOGIN_EXPIRED
    or parsed.get("data", {}).get("ret") == QZONE_CODE_IMAGE_EXPIRED   # ← 这里
):
```

它假设 `parsed["data"]` 一定是 dict。但**点赞接口返回的 `data` 是字符串** `""`：

```json
{ "code":0, "subcode":0, "message":"succ", "default":0, "data": "" }
```

于是在点赞时必然抛异常：

```
[AutoLike] 点赞失败 tid=aaaa1111bbbb2222cccc0004 uin=1000000004 昵称=好友C：
'str' object has no attribute 'get'

  File ".../core/qzone/client.py", line 67, in request
    or parsed.get("data", {}).get("ret") == QZONE_CODE_IMAGE_EXPIRED
```

**后果**：`like()` 里的异常会向上一路抛出，被 `AutoLike` 的 `except` 吞掉 → 记一条 `点赞失败`，然后**继续处理下一条**。
配合上游「失败也打印已点赞」的写法，日志会变得极其混乱。

**实测对比**：修复前一轮 5 条全失败；修复后一轮 5 条全成功。

**修复**：

```python
data_field = parsed.get("data")
...
or (isinstance(data_field, dict) and data_field.get("ret") == QZONE_CODE_IMAGE_EXPIRED)
```

### 根因 3：定时任务「错过 1 秒」就永久断链

上游 `core/scheduler.py` 的调度模型是**一次性任务链**：

```
注册任务 → 到点执行 do_task() → finally 里再排下一轮 → 到点执行 → ...
```

每轮用 `DateTrigger` 排一个只触发一次的任务：

```python
self.scheduler.add_job(
    func=self._run_task_wrapper,
    trigger=DateTrigger(run_date=target_time, timezone=self.timezone),
    name=f"{self.job_name}_once_{int(base_time.timestamp())}",
    max_instances=1,
    # ← 没有 misfire_grace_time
)
```

APScheduler 的默认宽限期只有 **1 秒**。一旦任务晚了（容器刚启动、事件循环卡顿、系统负载高），它会**直接跳过这次执行**：

```
Run time of job "AutoLike_once_1792171980 (trigger: date[2026-10-17 01:33:00 CST],
                 next run at: 2026-10-17 01:33:00 CST)" was missed by 0:00:01.048084
```

问题在于：**「排下一轮」这件事写在 `_run_task_wrapper()` 的 `finally` 里**。
任务被跳过 → wrapper 根本没被调用 → **下一轮永远不会被排上**。

结果：日志停在那一行 warning，之后**再也没有任何点赞动作，也没有任何报错** —— 安静的永久失效。这在 2 小时一次的低频任务上极其致命（你根本不会发现）。

**修复**：加宽限期，错过也补跑。

```python
misfire_grace_time=3600,   # 1 小时
coalesce=True,
```

**顺带发现的次生问题**：`_schedule_next_job()` 里，当随机偏移把执行时间算到过去时，会「立即补偿执行」（`now + 1s`）。此时 `_last_base_time` 仍是未来的基准时间，导致下一轮算出**同一个基准时间**、又可能再次补偿 —— 形成短时间内的连续执行。实测在 20 秒内连跑了 4 轮（每轮都会请求一次动态流）。

在 `0 */2 * * *` + `±900s` 的配置下，只有当执行时刻落进「基准点前 15 分钟」这个窗口才会触发，属于**偶发的 API 连击**，值得注意但不算致命。若要彻底解决，应改为「同一基准时间只允许执行一次」。

## 五、复现与自查方法

如果你的点赞也「看起来成功但没效果」，按下面顺序自查：

### 1. 用工具看真实状态

```bash
export QZONE_COOKIE='uin=oXXX; skey=XXX; p_skey=XXX; ...'
python3 tools/qzone_check.py --list
```

- 全是 `islike=0` → 赞根本没点上 → 检查 `like_use_http_key` 是否为 `true`
- 有 `islike=1` → 点赞正常，可能是浏览器缓存，强刷页面再看

### 2. 看日志里有没有崩溃

```bash
docker logs astrbot 2>&1 | grep -E "点赞失败|has no attribute|was missed by"
```

出现 `'str' object has no attribute 'get'` → 根因 2
出现 `was missed by` 且之后没有新日志 → 根因 3（任务链已断，重启 AstrBot 可临时恢复）

### 3. 手工发一次请求对照

把动态流 HTML 里那条动态的 `data-unikey` 原样复制出来，作为 `unikey`/`curkey` 发给：

```
POST https://user.qzone.qq.com/proxy/domain/w.qzone.qq.com/cgi-bin/likes/internal_dolike_app?g_tk=<g_tk>
```

其它参数：`qzreferrer` / `opuin` / `appid=311` / `from=1` / `typeid=0` / `abstime` / `fid` / `active=0` / `format=json` / `fupdate=1`。

> `g_tk` 由 `p_skey` 算出：`h=5381; for ch in p_skey: h += (h<<5) + ord(ch); g_tk = h & 0x7FFFFFFF`

---

## 六、给上游的建议

1. **`unikey`/`curkey` 改用 `http://` 拼接**（或直接复用动态流里的 `data-unikey`，最稳妥）。
2. `client.py` 中对 `data` 的取值加 `isinstance(data, dict)` 判断。
3. `add_job` 时设置 `misfire_grace_time`，且「排下一轮」不应只依赖 `finally`（任务被跳过就没人补排）。
4. `like_posts()` 应检查响应，失败时抛出而非静默记为成功。
5. README 中「点赞无效」的说明与 MIT 徽章都应更正（仓库 `LICENSE` 实为 GPL-3.0）。

## 附：排查时间线（简）

| 阶段 | 动作 | 结果 |
|---|---|---|
| 1 | Cookie 直连动态流接口 | ✅ `code:0`，拿到 90KB 数据 → Cookie 有效 |
| 2 | 直接调点赞接口 | 返回 `succ` → 一度误判为「成功」 |
| 3 | 用「详情接口含不含自己 uin」验证 | ⚠️ **假阳性**：那个 uin 出现在 `logininfo`（登录者自己），不是点赞列表 |
| 4 | 反复点赞同一条，比较响应差异 | 无差异 → 接口返回值不可作为证据 |
| 5 | 深挖动态流 HTML 的点赞按钮属性 | 🎯 发现 `data-islike` / `data-likecnt` → **找到裁判** |
| 6 | 对照浏览器 `data-unikey` 与插件拼的 unikey | 🎯 发现 `http://` vs `https://` → **根因 1** |
| 7 | 翻日志发现 `'str' object has no attribute 'get'` | 🎯 **根因 2** |
| 8 | 发现任务 `was missed by` 后再无日志 | 🎯 **根因 3** |
| 9 | 修复后闭环复测 | ✅ 5/5 全部 `islike=1` |

> 教训：**当一个"写操作"的返回值在所有情况下都相同，它就不能作为成功依据。必须找到能反映真实状态的读接口来交叉验证。**
